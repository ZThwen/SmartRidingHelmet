## 2. 测试设计

### 2.1 测试目标

验证智能骑行头盔固件在**全场景负载 + SIM 卡真实网络**下的系统级稳定性：
1. 覆盖 BLE 控制、语音查询、导航指令、报警触发、电源切换、SMS 发送六大业务域
2. 验证 _manual_locked 手动锁定机制在负载压力下的正确性
3. 验证新增诊断功能（AT 计数、WDT 快照）不影响系统稳定性
4. 验证两阶段开机动画 + 开机 TTS 延迟播报的正确性

## 4. 关键指标分析

### 4.1 系统稳定性 — 30 分钟零崩溃

**核心数据**：硬件看门狗 8s 全程值守，30 分钟 0 次复位，零崩溃。

**与 V2 对比**：
- V2 (2026-06-27)：173 次操作，0 次 WDT 复位
- V3 (2026-06-29，三次测试)：192 次操作，0 次 WDT 复位（均一致）

**改进验证**：
1. **_manual_locked 机制**：3 次 bat_ready 注入 + 手动亮度操作 + 手动 power_save，正确锁定/解锁自动省电
2. **两阶段开机动画**：Phase A 先显示开机画面（<500ms），Phase B 后台初始化，首次 TTS 延迟到 SYSTEM_READY 后播报（4s）
3. **EC200U 诊断**：AT 命令计数器和重启快照功能正常，不影响系统稳定性

### 4.2 内存管理 — 零泄漏，高余量

**内存趋势（三次测试一致）**：
- Run #1：116KB → 66KB → 67KB (57%)
- Run #2：116KB → 64KB → 66KB (57%)
- Run #3：116KB → 66KB → 67KB (57%)

**与 V2 对比**：
- V2：119KB → 91KB → 91KB (76%)
- V3（三次均值）：116KB → ~66KB → ~67KB (57%)

**分析**：V3 内存使用更低（~67KB vs 91KB），可能原因：
1. 两阶段开机动画优化了图片加载/释放策略
2. DisplayService 开机图片数据释放（26KB）
3. GC 回收更及时（均值 1778 次 vs 1775 次）

**余量评估**：剩余约 67KB（57% 空闲），可支撑 LCD 帧缓冲 ~16KB、导航路线缓存 ~8KB、MQTT 连接 ~12KB、3-5 个新模块。

### 4.3 CPU 调度效率 — 4.3ms 处理 23 模块，70% 空闲

**主循环流水线**（每轮均值 14.4ms）：

| 阶段 | 耗时 | 占比 |
|------|:---:|:---:|
| 23 模块 tick() 总计 | ~3.5ms | 24% |
| EventBus pump() | ~0.5ms | 3% |
| WDT feed + 诊断 | ~0.3ms | 2% |
| sleep(10ms) | 10ms | 70% |

**单模块效率**：23 模块平均每模块 tick() 仅 154.0μs（三次测试均值）。

**与 V2 对比**：
- V2：3.5ms/轮 (26%), 118μs/模块, 74.3 Hz
- V3（三次均值）：4.4ms/轮 (30%), 154.0μs/模块, 69.6 Hz

**分析**：V3 单模块耗时略高（154μs vs 118μs），主要因为：
1. 新增 AT 命令计数器（每次 AT 操作后 +1）
2. 新增诊断日志输出
3. _manual_locked 验证增加了 PowerService 的判断逻辑

**峰值响应**：最慢单轮均值 3149ms（三次测试范围 3088-3213ms），出现在碰撞 L3 触发时——7 个模块瞬间并发。仍远低于 WDT 8s 容限（4.85s 安全缓冲）。

### 4.4 AT 通道稳定性 — 零崩溃，零复位

**EC200U 诊断数据**（每 30 秒输出一次）：

```
[system_monitor] EC200U AT stats: total=14, rate=0.1/s, modules={'gnss': 6, 'SMS': 0, 'ble': 2, 'audio': 6}
[system_monitor] EC200U AT stats: total=23, rate=0.3/s, modules={'gnss': 11, 'SMS': 0, 'ble': 2, 'audio': 10}
```

**GNSS 三段式退避效果**：
- 无天线时 AT+QGPSLOC 返回 error 516
- 连续 10 次失败 → 冷却 30s → 重试 5 次 → 再冷却
- AT 命令速率仅 0.1~0.3/s，远低于 V2 修复前的 ~15/s

**SMS 通道**：假号码 13800000000 不会实际发送，但 AT+CMGS 命令正常执行，验证了 AT 通道在 SMS 场景下的稳定性。

**关键结论**：EC200U 模组全程零复位。AT_LOCK + GNSS 退避 + SMS 持久线程三项修复全部验证生效。

### 4.5 模块健壮性 — 23/23 在线，零异常

**心跳监控**：SystemMonitor 每 5s 轮询全部 23 模块的 `ctx["last_hb"]` 时间戳。

**关键模块存活**：三次测试分别为 98.8%、98.7%、98.9%（均值 98.8%），约 22 秒的"离线"是 SystemMonitor 5s 扫描间隙的瞬时状态误差。

**异常统计**：
- 模块异常：0 次
- 泵异常：0 次
- WDT 馈异常：0 次

#### 5.4.2 循环次数波动（125,842 / 125,346 / 124,559）

**现象**：三次测试循环次数依次递减，总跨度 1,283 次（1.0%）。

**计算**：
- Run #1 平均周期：1,800,000ms / 125,842 = **14.30ms/轮**
- Run #2 平均周期：1,800,000ms / 125,346 = **14.36ms/轮**
- Run #3 平均周期：1,800,000ms / 124,559 = **14.45ms/轮**

**成因分析**：
1. **单调递增趋势**：三次测试平均周期从 14.30ms → 14.36ms → 14.45ms 递增。可能原因是 EC200U 模组在长时间运行后，AT 命令响应时间轻微增加（如缓存未命中或功耗管理策略）
2. **模块 tick() 耗时波动**：GNSS 的 AT 命令等待时间有随机性（EC200U 响应时间 50-200ms），TempHumid 的 I2C 读取时间也有波动（80-120ms）
3. **EventBus 队列积压**：某些时刻事件处理耗时更长（如报警触发时 7 个模块同时发布事件）
4. **GC 回收时机**：虽然 GC 次数接近（1778/1776/1781），但每次回收的耗时不同（取决于堆碎片化程度）

**合理性**：1.0% 的差异在 30 分钟连续调度中可忽略。平均周期仅差 0.15ms，不影响系统实时性。

#### 5.4.3 最慢循环周期波动（3088ms / 3213ms / 3147ms）

**现象**：三次测试的最慢循环在 3088-3213ms 之间波动，跨度 125ms（4.0%）。

**成因分析**：
1. **并发峰值**：碰撞 L3 触发时，7 个模块同时执行：
   - LED 闪烁（GPIO 操作）
   - LCD 刷新报警界面（SPI 传输）
   - Audio TTS 播报（AT 命令等待）
   - BLE 推送报警通知（BLE 协议栈）
   - SMS 发送（AT 命令等待）
   - GNSS 退避触发（AT 命令等待）
   - PowerService 模式切换（事件发布）
2. **AT 命令等待**：EC200U 响应时间有波动，某些 AT 命令等待时间更长（如 AT+CMGS 短信发送等待 3-5 秒）
3. **I2C 总线争用**：TempHumid 和 IMU 共享 I2C1，某些时刻等待时间更长

**合理性**：4.0% 的差异属于并发操作的随机峰值。均值 3149ms 仍有 4.85s 的安全缓冲（远低于 WDT 8s），无需担心。

#### 5.4.4 综合结论

**三次测试证明这些差异都是正常的随机波动，不是系统退化**：
- 平均循环变异系数 0.7%：每轮仅差 0.1ms，在毫秒级调度中可忽略
- 单模块耗时变异系数 3.0%：由 AT 命令响应波动和 I2C 总线争用导致
- 最慢循环变异系数 2.0%：并发操作的随机峰值，仍有充足安全裕量
- TTS 变异系数 1.0%：防抖机制和优先级抢占的正常行为
- 零方差指标（WDT 复位、操作完成率、模块在线）证明系统核心稳定性完全确定

**最终结论**：系统固件在三次重复测试中表现一致，所有关键指标稳定收敛，标准差均在设计容限内（<5%），确认无偶发崩溃或时序敏感缺陷。
