## 第 1 章 系统整体设计

> **评委关注点**：你为什么选这个硬件平台？为什么不用 RTOS？架构怎么设计的？和其他方案比有什么优势？

### Q1. 为什么选择 STM32F413ZH + EC200U 这个硬件组合？和其他方案相比有什么优势？

**难度**：基础

**评委观察到的现象**：头盔上跑 MicroPython，有 BLE 直连手机，有 GNSS 定位，有语音播报。

**参考答案要点**：
1. STM32F413ZH：320KB SRAM + 1MB Flash，足够运行 MicroPython + 23 模块；NUCLEO 开发板便于竞赛快速验证
2. Quectel EC200U：集成 4G + GNSS + BLE + Audio + SMS 五合一模块，单芯片替代 5 个独立模块，降低硬件复杂度和成本
3. 对比其他方案：
   - ESP32 方案：WiFi 不适合骑行户外场景，BLE 4.2 不如 EC200U 稳定，无蜂窝通信
   - STM32 + 外挂 BLE/GNSS 模块：多芯片增加 PCB 面积和功耗，EC200U 五合一更紧凑
   - 纯 EC200U（无 STM32）：EC200U 的 MicroPython 不支持外设 DMA/TIM，无法驱动 PWM 灯和 LCD
4. MicroPython 选择：快速开发 + 交互调试（Thonny REPL），竞赛时间紧迫比 C 更快出原型

**评委可能追问**：
- "MicroPython 性能够吗？" → 实测单模块 154μs，调度 69.6Hz，CPU 70% 空闲，性能充裕
- "为什么不选 RTOS（FreeRTOS）？" → MicroPython 在 EC200U 上更易调试，23 模块用事件驱动已满足实时性；RTOS 开发周期更长

### Q2. 系统架构是怎么设计的？为什么要分层？

**难度**：基础

**评委观察到的现象**：23 个功能模块同时运行，碰撞报警时其他功能不卡顿。

**参考答案要点**：
1. 四层架构：App（主循环调度）→ Service（业务逻辑）→ Device（硬件封装）→ Vendor（底层固件，只读）
2. 分层的好处：
   - 换硬件只改 Device 层（如心率从 UART9 换 UART5，上层无感知）
   - 模块间不直接调用，通过事件总线通信（碰撞检测不依赖报警模块，解耦）
   - 23 模块独立开发测试，多人并行不冲突
3. 事件驱动：碰撞检测发布"碰撞事件"，报警模块订阅后处理；新增功能只需订阅事件，不改已有模块（开闭原则）

**评委可能追问**：
- "事件驱动有什么缺点？" → 延迟一个 tick（约 10ms），但骑行场景足够；忘记处理事件会导致功能失效（已有防御机制）
- "23 模块同时运行会不会冲突？" → 主循环串行调度每模块 tick，每轮 <5ms，总计 3.5ms，不冲突

### Q3. 开机时先看到画面、后台还在初始化，这个体验是怎么实现的？

**难度**：中级

**评委观察到的现象**：开机后 <1s 显示开机画面，3s 后系统就绪，期间画面不消失。

**参考答案要点**：
1. 两阶段初始化设计：
   - Phase A：LCD + 显示服务先初始化，立即显示开机画面（<500ms）
   - Phase B：21 个模块后台初始化，LCD 硬件自主刷新保持画面显示
2. LCD 的 ST7735 有硬件自主刷新机制，一旦写入画面数据，不需要 CPU 持续驱动就能保持显示
3. Phase B 内部有顺序约束：传感器先→执行器次→心率最后（因为心率 UART 初始化会破坏通信通道）→系统监控最后（确保覆盖全部模块）

**评委可能追问**：
- "为什么心率必须最后初始化？" → 心率传感器原来用的 UART9 初始化会破坏 EC200U 的 AT 通信通道，导致音频/BLE/SMS/GNSS 全部超时；换成 UART5 后问题解决，但仍保持顺序约束作为防御
- "如果某个模块初始化失败怎么办？" → 主循环跳过该模块的 tick，系统监控会告警；关键模块（碰撞/报警/BLE）失联则系统复位重启

### Q4. 系统怎么保证实时性？23 个模块同时运行会不会卡顿？

**难度**：中级

**评委观察到的现象**：碰撞后 <15ms 触发报警，语音播报不延迟，LCD 不卡顿。

**参考答案要点**：
1. 主循环调度：每轮 10ms 周期，23 模块各执行一次 tick（平均 154μs/模块），总计 3.5ms
2. 时间片控制：传感器不是每 10ms 都采集——温度 2s 采一次，心率 2s 采一次，IMU 100ms 采一次；tick 内用时间守卫，未到采样间隔立即返回
3. 实测数据：主循环 14.4ms（含 10ms sleep），调度 69.6Hz，CPU 70% 空闲；30 分钟压力测试 0 次 WDT 复位
4. 峰值场景：碰撞 L3 触发时 7 模块并发（LED+LCD+Audio+BLE+SMS+GNSS+Power），最慢循环 3149ms，仍远低于 8s 看门狗阈值

**评委可能追问**：
- "10ms sleep 会不会影响响应速度？" → 碰撞检测在 IMU tick 中实时判决（<1ms），报警在下一轮 pump 触发（<10ms），总延迟 <15ms
- "如果扩展到更多模块呢？" → 当前 23 模块 tick 3.5ms，扩展到 40 模块约 6.2ms，仍有余量

### Q5. 为什么用 MicroPython 不用 C 语言？性能够吗？

**难度**：中级

**评委观察到的现象**：系统流畅运行，碰撞检测快速响应。

**参考答案要点**：
1. 选 MicroPython 的理由：
   - 竞赛时间紧迫，MicroPython 开发效率比 C 高 3-5 倍（交互式 REPL 调试）
   - EC200U 官方提供 MicroPython SDK，C 语言开发 EC200U 需要 Quectel SDK 编译环境更复杂
   - 23 模块快速迭代，用 Python 写事件驱动架构更自然
2. 性能实测足够：
   - 单模块 tick 154μs，调度 69.6Hz，CPU 70% 空闲
   - 碰撞检测 <1ms 响应，报警 <15ms 触发
   - 峰值 3149ms（远低于 WDT 8s）
3. 什么时候需要 C：实时性要求 <1ms 的场景（如电机 PID），本项目不需要

**评委可能追问**：
- "MicroPython 有什么坑？" → GC 碎片化（线程栈不回收）、__doc__ 属性不存在、f-string 格式化瘦身时会丢失精度——都已踩过并解决
- "如果要做产品量产，还会用 MicroPython 吗？" → 量产会考虑 C 语言优化关键路径，但竞赛阶段 MicroPython 是最优选择

### Q6. 为什么选 BLE 直连不用 MQTT 云端通信？

**难度**：中级

**评委观察到的现象**：手机靠近头盔就能连接控制，不需要联网，不需要服务器。

**参考答案要点**：
1. BLE 直连优势：
   - 低延迟（<100ms vs MQTT 秒级）
   - 无云端依赖（断网仍可用，骑行户外场景必须有）
   - 架构简单（Device↔BLE↔小程序 vs Device↔MQTT↔Cloud↔HTTP↔小程序）
   - 节省内存（废弃 CloudService/Network/MQTT/Qth 四个模块，释放 ~12KB）
2. BLE 直连劣势：
   - 距离限制（10-30m），骑行场景手机在口袋/车把足够
   - 手机必须与头盔在同一蓝牙范围
3. MQTT 方案问题：HTTP 轮询延迟高、云端断网不可用、MQTT 连接占 12KB 内存、架构复杂四级转发

**评委可能追问**：
- "如果需要云端存储骑行历史？" → 小程序端负责云端上传（微信云开发），头盔只管 BLE 推送实时数据
- "BLE 连接稳定性怎么样？" → 30 分钟压力测试 192/193 操作成功，99.5% 通过率

### Q7. 系统有多少模块？扩展性怎么样？

**难度**：基础

**评委观察到的现象**：功能丰富（碰撞/心率/导航/语音/灯光/控制/报警），且运行流畅。

**参考答案要点**：
1. 23 个模块：6 传感器 + 6 执行器/接口 + BLE + SMS + 9 Service
2. 扩展性设计：
   - 事件驱动：新增功能只需新增模块+订阅事件，不改已有模块
   - 四层架构：更换硬件只改 Device 层
   - 性能余量：CPU 70% 空闲，内存 67KB（57%）空闲，可支撑 3-5 个新模块
3. 新增模块流程：继承基类 → 定义配置/数据 → 实现周期调度 → 定义事件 → 集成到主循环 → 测试

**评委可能追问**：
- "如果要加 CO2 传感器？" → 只需新增 Device 层驱动 + Service 层处理 + BLE 推送新字段，不改碰撞/报警等其他模块
- "加新模块会影响性能吗？" → 当前 tick 3.5ms，新加一个约 154μs，40 模块总计约 6.2ms，不影响实时性

## 第 2 章 碰撞检测与报警系统

> **评委关注点**：碰撞检测是怎么做的？误报怎么防？分级报警有什么意义？报警响应速度？

### Q8. 碰撞检测是怎么做的？敲桌子和摔地上怎么区分？

**难度**：中级

**评委观察到的现象**：演示中敲板子触发 L1/L2 报警，摔落触发 L3 SOS；桌面平移和抖动不误报。

**参考答案要点**：
1. 三级判决流程：
   - 第一级：加速度归一化为 g 值（1g=9.8m/s²）
   - 第二级：滑动窗口 15 样本（1.5s）+ 四级阈值：<1.5g 丢弃、1.5-5g 可疑需鉴别、5-8g 高度疑似、>8g 确定碰撞直判 L3
   - 第三级：三个防误报鉴别器串联
2. 三个鉴别器：
   - 脉冲宽度鉴别：真实碰撞脉冲 >60ms，桌面平移是对称窄尖峰 <60ms → 排除平移/拿取
   - 失重前兆检测：摔落前有短暂失重（<0.8g）+ 大脉冲 → 增强摔落识别
   - 振荡判别：桌面抖动是持续振荡（方差 >0.5g² + 波峰 >3），敲击是瞬时能量集中 → 排除抖动
3. 实测验证：6 种场景（摔落/敲击/抖动/拿取/平移/静止），只有摔落和敲击触发报警

**评委可能追问**：
- "为什么用滑动窗口不单点判断？" → 单点无法区分脉冲宽度、振荡特征，窗口提供时间维度信息
- "阈值怎么调的？" → 先实况测试摸底，从 1.2g 逐步提高到 1.5g 稳定；裸板无外壳，摔落峰值比戴头盔低（5-8g）

### Q9. 碰撞等级 L1/L2/L3 分别对应什么情况？L3 为什么升级为 SOS？

**难度**：基础

**评委观察到的现象**：轻敲板子→LED慢闪+短报警音→30s自动取消；重敲/摔落→LED快闪+急促报警音+SOS短信→不自动取消。

**参考答案要点**：
1. 等级判定：
   - L1 轻微（1.5-5g）：轻敲板子，LED慢闪(1s)+等级1报警音，30s自动取消
   - L2 中等（5-8g）：中等敲击，LED中速闪(500ms)+等级2报警音，30s自动取消
   - L3 严重（>8g）：摔落/重敲，LED快闪(200ms)+等级3报警音，升级为 SOS
2. L3 升级 SOS 的原因：严重碰撞用户可能已昏迷无法手动取消，需要持续报警直到救援到达
3. SOS 特性：无自动超时（与 L1/L2 的 30s 自动取消不同），必须手动确认取消
4. 报警多通道同步：本地声光 + BLE 推送手机 + SMS 发紧急联系人 + LCD 报警界面 + TTS 播报

**评委可能追问**：
- "L1/L2 30s 自动取消会不会太短？" → 轻微碰撞不需要持续报警，30s 提醒后自动恢复；如果用户认为严重可在手机端手动升级
- "报警音和导航语音冲突怎么办？" → 报警优先级 > 导航语音，报警期间导航语音被暂停

### Q10. 演示中碰撞后多长时间报警？响应速度怎么保证？

**难度**：中级

**评委观察到的现象**：碰撞后几乎立即看到 LED 闪烁和听到报警音。

**参考答案要点**：
1. 响应链路：IMU 采集(100ms/次) → 碰撞检测实时判决(<1ms) → 事件入队 → pump 触发回调(<10ms) → 报警启动 → LED闪烁+报警音+BLE推送+SMS发送
2. 总延迟 <15ms（从碰撞检测到报警启动）
3. SMS 发送在持久线程中执行(3-5s)，不阻塞主循环；BLE 推送 <100ms
4. LED 和报警音在 pump 回调中立即启动（微秒级硬件操作）
5. 密集指令时快照合并推送：每次控制状态变更不再推送 3 条消息，合并为 1 条，避免 BLE 队列爆炸

**评委可能追问**：
- "SMS 发送 3-5s 会不会延迟？" → SMS 是异步发送，本地声光和 BLE 推送在 <15ms 内已触发，SMS 是补充通知渠道
- "如果连续碰撞怎么办？" → 两次碰撞最短间隔 3000ms 防重复触发；L3 SOS 期间再碰撞不重复发 SMS

### Q11. 碰撞报警的误报率怎么样？怎么验证的？

**难度**：高级

**评委观察到的现象**：演示中桌面平移、拿取、抖动都不触发报警。

**参考答案要点**：
1. 防误报机制：三级判决 + 三鉴别器串联
   - 脉冲宽度鉴别排除桌面平移（窄尖峰 <60ms）
   - 振荡判别排除桌面抖动（方差 >0.5g² + 波峰 >3）
   - 失重前兆增强摔落识别（失重 + 大脉冲 = 真摔落）
2. 6 种实测场景验证：
   - 摔落地面 20-100+g → 正确检测 L3 ✅
   - 敲击 3-15g → 正确检测 L1-L3 ✅
   - 桌面抖动 2-4g → 正确排除 ✅
   - 拿起 1.5-3g → 正确排除 ✅
   - 桌面平移 2-3g → 正确排除 ✅
   - 静止 ~1g → 正确排除 ✅
3. 参数调优方法：先用实况测试脚本摸底，从低阈值逐步提高到稳定，再验证全场景
4. 防重复触发：两次碰撞最短间隔 3000ms，裸板碰撞后稳定较快

**评委可能追问**：
- "真实骑行场景和裸板测试有什么区别？" → 裸板无头盔外壳缓冲，摔落峰值更低(5-8g)；戴头盔后峰值更高(20-100+g)，阈值仍覆盖
- "如果骑行颠簸路面持续振动？" → 振荡判别器排除持续振动（方差 >0.5g² + 波峰 >3），不会误报

### Q12. SOS 报警时短信发什么内容？位置信息怎么获取？

**难度**：基础

**评委观察到的现象**：碰撞后手机收到短信包含位置链接。

**参考答案要点**：
1. SMS 内容：报警类型 + 高德地图链接 `https://uri.amap.com/marker?location=经度,纬度`
2. 位置获取：EC200U 内置 GNSS 定位，获取经纬度后生成高德地图链接
3. 紧急联系人配置：用户通过小程序 BLE 设置手机号（set_phone 指令），头盔存储后供报警使用
4. SMS 在持久线程异步发送（不阻塞主循环），AT 命令有超时机制
5. GNSS 无信号时：SMS 中位置可能缺失或使用最后已知位置

**评委可能追问**：
- "高德地图链接为什么不用百度地图？" → 高德地图 URI API 更简洁，骑行场景高德更常用
- "短信发送失败怎么办？" → 本地声光和 BLE 推送不受影响，SMS 是补充通知渠道

### Q13. 报警怎么取消？手机端和头盔端都可以吗？

**难度**：基础

**评委观察到的现象**：手机端点击确认后报警停止，物理按键也可以取消。

**参考答案要点**：
1. 手机端取消：小程序点击确认 → BLE FFF4 写入 → 头盔接收 → AlarmService 取消报警
2. 头盔端取消：物理按键按下 → ButtonDriver IRQ → EVENT_BUTTON_PRESS → AlarmService 取消
3. L1/L2 自动取消：30s 后自动取消（轻微碰撞不需要持续报警）
4. L3/SOS 不自动取消：必须手动确认（严重碰撞用户可能昏迷，需持续报警到救援）
5. 报警取消后：LED 停止闪烁、报警音停止、LCD 恢复正常界面、BLE 推送取消通知(t=6)

**评委可能追问**：
- "如果用户昏迷无法手动取消 SOS？" → SOS 会持续报警（声光+BLE+短信），直到有人发现并确认；这是设计意图——持续报警确保救援
- "30s 自动取消后用户还想继续报警？" → 可在手机端手动触发 SOS，或物理按键触发

### Q14. 静默报警是什么场景用的？

**难度**：中级

**评委观察到的现象**：演示中有"静默报警"指令选项。

**参考答案要点**：
1. 静默报警：无 LED 闪烁、无报警音，仅 BLE 通知手机（手机端弹窗+震动）
2. 适用场景：骑行中不想打扰周围人（如夜间安静社区），但需要让手机端知道发生了碰撞
3. 实现：AlarmService 启动静默报警模式 → LED 不闪、Audio 不播 → BLE 推送 t=5 报警通知 → 手机端提醒用户
4. 用户可在小程序端选择"静默报警"模式，或在语音指令中说"静默报警"

**评委可能追问**：
- "静默报警和 L1 报警有什么区别？" → L1 有声光提醒（本地可感知），静默只有手机端通知（远程可感知）；静默更适合不想打扰他人的场景
- "静默报警期间导航语音还能播吗？" → 静默报警 alarm_playing=False，导航 TTS 不受阻塞（与有声报警不同）

### Q15. 碰撞检测的滑动窗口是怎么工作的？

**难度**：高级

**评委观察到的现象**：连续敲击多次，每次都能正确识别等级。

**参考答案要点**：
1. 滑动窗口：保留最近 15 个加速度样本（约 1500ms），每个样本包含 {g值, 时间戳}
2. 工作流程：新数据进入窗口 → 超时数据自动淘汰 → 在窗口内找峰值 → 根据峰值高度判断等级 → 鉴别器验证脉冲特征
3. 窗口大小 15 的设计：IMU 采样 100ms/次，15 样本=1500ms，覆盖碰撞脉冲(60-300ms) + 前后上下文
4. 边缘跳过逻辑：峰值位于窗口最右边缘时跳过判决，等下一轮数据让峰值进入窗口内部（避免脉冲宽度误判）
5. 防重复触发：两次碰撞最短间隔 3000ms

**评委可能追问**：
- "为什么窗口是 15 不是 20？" → 15 样本=1500ms 覆盖典型碰撞脉冲(60-300ms)及其上下文；更长窗口增加延迟和计算量
- "边缘跳过逻辑有什么用？" → 5g 敲击的邻居 2.5g 未到达时脉冲宽度算为 0，真实碰撞会被拦截；等待下一轮让峰值进入内部再判决

## 第 3 章 BLE 通信与远程控制

> **评委关注点**：手机怎么控制头盔？BLE 通信怎么设计？数据怎么压缩？为什么不用 WiFi？

### Q16. 手机怎么远程控制头盔？指令怎么传递的？

**难度**：基础

**评委观察到的现象**：小程序点击"开灯"→头盔灯亮；点击"音量+"→头盔 TTS 播报确认。

**参考答案要点**：
1. 控制链路：小程序 → BLE FFF3 特征值写入控制指令 → 头盔 BLE 中断接收 → 缓存到环形缓冲区 → 主循环解析路由 → ControlService 执行 → 状态回推手机
2. 27 条控制指令：灯光（开/关/自动/亮度+/亮度-/闪烁）、音量（+/−）、电源（省电/正常/紧急）、报警（取消/SOS/静默）、配置（设置紧急联系人手机号）
3. 状态回推闭环：ControlService 执行后 → 更新控制状态 → BLE 推送 t=7 合并消息 → 小程序更新 UI → 确认指令生效
4. 中断只写缓冲区（微秒级返回），主循环统一处理（不阻塞）

**评委可能追问**：
- "指令执行失败怎么反馈？" → 无论成功失败都回推当前状态，手机对比预期判断是否成功
- "密集指令会丢吗？" → 快照合并保证最新状态不丢，中间状态被覆盖（快速调亮度 10→20→30，只推送 30）

### Q17. BLE 数据是怎么压缩的？为什么需要压缩？

**难度**：中级

**评委观察到的现象**：小程序显示的数据实时更新，BLE 连接稳定。

**参考答案要点**：
1. ATT_MTU 限制：BLE 默认 MTU=23（可用载荷仅 20 字节），协商后可达 247（载荷 244 字节）
2. 压缩格式：短字段名 + 数字编码，如 `{"t":7,"m":1,"b":50,"v":5,"p":0}` 仅 30 字节
3. 为什么要压缩：
   - 传感器合并数据 t=0 包含 11 个字段（温湿度/位置/速度/光照/电量/心率/血氧），不压缩会超 MTU
   - 报警通知 t=5 仅 15 字节 `{"t":5,"a":1,"l":2}`
   - 事件总线会自动注入 source/timestamp 导致膨胀（16 字节→66 字节），转发时需剥离
4. 消息类型：t=0 传感器数据、t=5 报警、t=6 取消、t=7 控制状态、t=99 心跳

**评委可能追问**：
- "MTU 协商什么时候做？" → BLE 连接建立后自动协商，手机端发起 MTU exchange
- "如果不压缩会怎样？" → notify 返回 `+CME ERROR: 53`，消息发送失败

---

### Q18. BLE GATT 四个通道各自干什么？

**难度**：中级

**评委观察到的现象**：小程序有骑行数据展示、导航提示、控制按钮、报警确认四个功能。

**参考答案要点**：
1. FFF1（NOTIFY，头盔→手机）：传感器合并数据推送，每 tick 周期推送一次
2. FFF2（WRITE，手机→头盔）：导航指令通道，每 5s 下发转弯方向/距离/路名
3. FFF3（WRITE，手机→头盔）：骑行控制通道，27 条控制指令
4. FFF4（WRITE，手机→头盔）：报警确认通道，用户确认收到报警
5. 按功能分离特征值：每个通道独立事件，不同模块各自处理，符合解耦原则

**评委可能追问**：
- "为什么用 NOTIFY 不用 INDICATE？" → NOTIFY 不需要客户端确认，延迟更低(<100ms)，适合实时数据；INDICATE 需确认增加延迟
- "为什么不合并成一个通道？" → 功能分离便于解耦（导航/控制/报警各自独立事件），且不同指令类型不会混淆

---

### Q19. 手机密集发指令时 BLE 会不会崩溃？

**难度**：高级

**评委观察到的现象**：快速连续点击亮度调节，每次头盔都响应，不卡顿。

**参考答案要点**：
1. 原方案问题：每次状态变更推送 3 条 notify（灯光+音量+电源），密集指令 1 秒 5 次=15 条 notify，AT 命令堆积导致死机
2. 快照合并方案：合并 3 条为 1 条 `{"t":7,"m":1,"b":50,"v":5,"p":0}`，每次 tick 只推送 1 条
3. 中断只写环形缓冲区（微秒级返回），不阻塞 BLE 协议栈
4. 缓冲区满时丢弃最旧指令（控制指令最新状态最重要，丢弃旧的只保留最新不影响功能）
5. 30 分钟压力测试：密集指令场景 192/193 操作成功，99.5% 通过率

**评委可能追问**：
- "丢弃旧指令会不会丢失关键信息？" → 控制指令是状态型（如亮度 50%），不是事件型（如碰撞）；保留最新状态即可
- "1 秒 10 次指令测试怎么样？" → 不崩溃，快照合并保证最多 1 条/tick 推送

### Q20. BLE 连接断开后怎么重连？

**难度**：中级

**评委观察到的现象**：BLE 断连后重新连接可以恢复数据和控制。

**参考答案要点**：
1. BLE 广播：EC200U BLE 作为 GATT Server 广播 "SmartHelmet-66ccff"，手机作为 Central 主动扫描连接
2. 重连处理：适配器已打开时报 "already open" → 捕获后更新回调直接扫描（不重新 open，避免断开已有连接）
3. 连接后延迟推送：手机需要时间完成 CCCD 订阅（订阅 notify 特征值），立即推送大数据会导致丢失
4. 特征值监听过滤：BLE 数据回调监听所有特征值变化，必须按 characteristicId 过滤（FFF1/FFF2/FFF3/FFF4）

**评委可能追问**：
- "BLE 有效距离多少？" → BLE 4.2 约 10-30m，骑行场景手机在口袋/车把足够
- "断连期间碰撞报警怎么办？" → 本地声光报警不受影响，BLE 推送丢失但 SMS 紧急联系人仍可收到

### Q21. AT 命令通道是串行的，多模块同时用会冲突吗？

**难度**：高级

**评委观察到的现象**：导航播报+GNSS定位+SMS发送同时工作，不卡顿。

**参考答案要点**：
1. EC200U AT 通道是串行的：BLE/GNSS/Audio/SMS 都用 AT 命令，同一时刻只能一个模块使用
2. AT_LOCK 全局互斥锁：保证同一时刻只有一个模块在用 AT 通道
3. GNSS 三段式退避：无天线时持续重试会占用 AT 通道（~15 次/s），退避策略：10 次失败→30s 冷却→5 次重试→再冷却；AT 速率降到 0.1-0.3/s
4. SMS 在持久线程中异步执行：主循环只 put 到队列，后台线程消费，不阻塞其他模块
5. 实测：30 分钟压力测试，4 模块 AT 命令速率稳定 0.1-0.3/s，EC200U 零复位

**评委可能追问**：
- "SMS 发送时其他模块 AT 命令怎么办？" → 等待锁释放；SMS 在持久线程中执行，主循环不阻塞
- "如果 AT 命令超时怎么处理？" → 各模块 AT 命令有超时机制，超时后返回错误不阻塞

### Q22. 为什么不用 WiFi 代替 BLE？

**难度**：中级

**评委观察到的现象**：手机靠近头盔就能连接，不需要 WiFi 热点。

**参考答案要点**：
1. WiFi 不适合骑行场景：
   - 骑行户外没有 WiFi 热点
   - WiFi 功耗远高于 BLE（BLE 4.2 低功耗设计）
   - WiFi 配对复杂（需要 SSID/密码），BLE 扫描即连
2. BLE 直连优势：
   - 低功耗（BLE 4.2 低功耗模式）
   - 即连即用（扫描→连接→使用）
   - 低延迟（<100ms）
   - 无需基础设施（手机直连头盔）
3. EC200U 有 WiFi 模块但未使用：BLE 已满足所有通信需求，WiFi 无额外价值

**评委可能追问**：
- "BLE 和 WiFi 功耗差多少？" → BLE 4.2 连接态约 10-15mA，WiFi 连接态约 100-200mA，差距 10 倍
- "如果要支持多手机同时连接？" → BLE GATT Server 理论支持多连接，但 EC200U BLE 实际只支持 1 个 Central；可考虑 WiFi AP 模式

## 第 4 章 传感器与数据融合

> **评委关注点**：多传感器数据怎么合并推送？心率怎么检测？数据准确吗？

### Q23. 多传感器数据怎么合并到手机上的？

**难度**：中级

**评委观察到的现象**：小程序骑行主页同时显示温度/湿度/速度/位置/光照/电量/心率/血氧，全部实时更新。

**参考答案要点**：
1. 数据来源：6 个传感器各自 tick 周期采集 → 发布事件（EVENT_XXX_READY）
2. BLEService 统一缓存：订阅所有传感器事件，缓存最新值
3. 合并推送：每 tick 周期组装 1 条 t=0 消息 `{"t":0,"d":{"tmp":25,"hum":60,"lat":30.5,...}}`，11 字段合并为 1 条 notify
4. 为什么合并不分别推送：减少 notify 次数和 AT 命令，避免队列爆炸；合并后 1 条/tick
5. LCD 同步展示：DisplayService 订阅传感器事件 → 缓存最新值 → tick 周期渲染英文布局界面

**评委可能追问**：
- "11 个字段会不会超 BLE 载荷？" → ATT_MTU 协商后载荷 244 字节，11 字段压缩约 80 字节，不超限
- "传感器采样频率不同怎么合并？" → BLEService 缓存各传感器最新值，不论采样频率，每 tick 统一推送最新快照

---

### Q24. 心率/血氧是怎么检测的？数据准确吗？

**难度**：中级

**评委观察到的现象**：小程序显示实时心率(如 72bpm)和血氧(如 98%)。

**参考答案要点**：
1. 硬件：MKS SPO2-ZS-BLE 心率血氧传感器，通过 UART5 连接（115200 波特率）
2. 数据包格式：50 字节帧，帧头 0xFF，第 41 字节心率(bpm)，第 42 字节血氧(%)
3. 5 重验证保证数据准确：
   - 长度必须正好 50 字节
   - 帧头必须是 0xFF
   - 心率范围验证（合理范围才接受）
   - 血氧范围验证
   - 预热期检查（传感器启动 10s 内数据不稳定，丢弃）
4. 脱落/超时检测：正常模式 6s 超时、省电模式放宽为 21s；超时置 valid=False
5. 防阻塞：每次 tick 最多处理 2 帧，防止大量数据阻塞主循环

**评委可能追问**：
- "为什么有 10s 预热期？" → 传感器刚启动时光电信号不稳定，预热期内数据丢弃不推送
- "手指脱落时怎么处理？" → 6s 超时检测，脱落后 valid=False，小程序显示"心率传感器脱落"

---

### Q25. 温湿度/光照/电量是怎么检测的？

**难度**：基础

**评委观察到的现象**：LCD 和小程序实时显示温度/湿度/光照强度/电量百分比。

**参考答案要点**：
1. AHT20 温湿度：I2C1 总线（地址 0x38），每 2s 采集一次
2. GL5528 光敏电阻：ADC PC5 读取（0-65535），映射到光照强度 → 自适应灯光亮度
3. 电池电量：ADC 分压检测，6 档映射（0-100%），低电量自动告警/省电
4. IMU 加速度：I2C1 总线（地址 0x19），每 100ms 采集，用于碰撞检测
5. I2C1 共享总线：AHT20 和 IMU 共享，通过设备地址区分（0x38/0x19）

**评委可能追问**：
- "光照传感器怎么控制灯光？" → 光照 ADC 值 → gamma 非线性映射 → PWM 亮度百分比；人眼对光感知是对数的，gamma 映射使感知更线性
- "I2C 共享总线会不会冲突？" → I2C 协议通过设备地址区分，每个传感器有独立地址，不冲突

### Q26. 自适应灯光是怎么工作的？

**难度**：中级

**评委观察到的现象**：环境变暗时头盔灯自动变亮，环境变亮时自动变暗。

**参考答案要点**：
1. 数据流：光照传感器 ADC → LightService → gamma 非线性映射 → PWM 亮度
2. gamma 映射原理：人眼对光的感知是对数的，线性 PWM 调光低亮度变化过快、高亮度变化过慢；gamma 映射（γ≈2.2）使感知亮度变化更线性
3. 18W 大功率灯散热限制：峰值限制 50%（防止过热），PWM 占空比最大 0.5
4. 自动/手动模式：
   - 自动模式：光照 ADC → gamma → PWM
   - 手动模式：用户通过 BLE/语音直接设置亮度
   - 手动后锁定自动模式（用户调亮度后不会被自动模式覆盖，除非用户主动选择"省电"）
5. PWM 硬件：PE11 TIM1_CH2，PWM 调光

**评委可能追问**：
- "gamma 值怎么选的？" → 通常 2.2（sRGB 标准），根据实际人眼感受调试
- "50% 峰值限制会不会太暗？" → 18W 灯 50% 仍有 9W，足够骑行照明；散热安全优先

---

### Q27. 6 档电量检测是怎么做的？低电量有什么表现？

**难度**：基础

**评委观察到的现象**：小程序和 LCD 显示电量百分比，低电量时有告警提示。

**参考答案要点**：
1. 硬件：自研电源检测拓展板（防反接+滤波+分压检测），ADC 读取电池电压
2. 6 档映射：电池电压 → 百分比（0-100%）→ 发布事件
3. 低电量行为：
   - 正常电量：全功能正常（ACTIVE 模式）
   - 低电量：告警提醒 + 显示提示
   - 严重不足：自动切 EMERGENCY 模式（心率/温度停止，保留碰撞检测/报警/BLE）
4. 启动宽限期：前 3 次采样不触发事件（避免启动时 ADC 不稳定误判）
5. 恢复机制：电量恢复后取消告警，恢复 ACTIVE 模式

**评委可能追问**：
- "EMERGENCY 模式下心率停止，用户怎么看心率？" → 最后已知值保留，标记失效(valid=False)；核心安全功能（碰撞/报警/BLE）不中断
- "电量极低时系统会不会崩溃？" → CRITICAL 模块（碰撞/报警/BLE）仍运行；如果也卡死，WDT 8s 复位重启恢复

## 第 5 章 导航与语音交互

### Q28. 导航是怎么播报转弯指令的？完整链路是什么？

**难度**：中级

**评委观察到的现象**：小程序规划路线后，头盔 TTS 播报"前方 200 米左转"。

**参考答案要点**：
1. 完整链路：
   - 小程序端：腾讯地图 API 规划路线 → 每 5s 计算下一步转弯 → BLE FFF2 写入指令
   - 头盔端：BLE 接收 → cmd_buffer 缓存 → tick 解析 → 事件路由 → NavigationService → AudioDriver TTS 播报
2. 导航指令内容：8 种方向（直行/左转/右转/掉头/左前方/右前方/左后方/右后方）+ 距离 + 路名
3. 头盔只做播报：路径规划在小程序端（腾讯地图 API 需要 HTTP），头盔只接收简短指令 + TTS 播报
4. BLE 直连低延迟：指令传输 <100ms，无云端依赖
5. TTS 在持久线程中执行：避免每次创建新线程的内存碎片化

**评委可能追问**：
- "为什么路径规划在小程序端？" → 腾讯地图 API 需要 HTTP 请求，头盔无 HTTP 能力；小程序计算后只需下发简短指令
- "导航 TTS 和报警 TTS 冲突？" → 报警优先级 > 导航，报警期间导航 TTS 被暂停

**评委可能追问**：

## 第 6 章 电源管理与可靠性

> **评委关注点**：低电量怎么办？系统崩溃怎么恢复？看门狗有什么用？长时间运行稳定吗？

### Q34. 低电量时系统怎么降级？安全功能会不会中断？

**难度**：中级

**评委观察到的现象**：低电量告警后心率/温度停止更新，但碰撞检测/报警/BLE 仍正常。

**参考答案要点**：
1. 四模式电源策略：
   - ACTIVE：全部正常采样
   - SUSPENDED：温度 30s/光照停止/GNSS 10s/心率降频
   - EMERGENCY：温度停止/光照停止/GNSS 10s/心率停止，保留碰撞/报警/BLE
2. EMERGENCY 模式安全保证：
   - 碰撞检测（IMU 仍每 100ms 采样）→ 碰撞报警仍可触发
   - 报警流程（LED+Audio+SMS+BLE）→ 四通道报警不中断
   - BLE 通信 → 手机仍可控制和接收数据
3. 停止采样的模块仍更新心跳：避免系统监控误判离线触发看门狗复位
4. 手动锁定机制：用户手动调亮度后，自动省电不会覆盖用户设置（除非用户主动选择"省电"）

**评委可能追问**：
- "EMERGENCY 模式下心率怎么看？" → 最后已知值保留（标记失效），小程序可显示"心率数据已过期"
- "电量恢复后自动恢复吗？" → 是，电量恢复后自动切回 ACTIVE 模式，取消低电量告警

### Q35. 系统有看门狗，为什么不无条件喂狗？

**难度**：高级

**评委观察到的现象**：系统长时间运行稳定，但评委可能追问如果关键模块卡死怎么办。

**参考答案要点**：
1. 看门狗（WDT 8s）门控逻辑：
   - 启动宽限期（前 15s）：无条件喂狗（模块还在初始化）
   - 正常模式：只有 3 个 CRITICAL 模块（碰撞/报警/BLE）都存活才喂狗
   - 安全模式：任意模块存活即可喂狗（连续 5 次 WDT 复位后放宽）
2. 不无条件喂狗的原因：如果碰撞检测模块卡死，无条件喂狗会让系统"假活"——WDT 不复位但安全功能失效；停喂 WDT 让系统复位重启，恢复安全功能
3. CRITICAL 模块失联 → 停喂 WDT → 8s 后系统复位 → 重启恢复安全功能
4. 安全模式设计：连续 5 次 WDT 复位可能是某个 CRITICAL 模块 bug 导致反复卡死；放宽检测让系统先运行，5 分钟稳定后恢复正常模式

**评委可能追问**：
- "复位后数据会丢失吗？" → 运行时数据在 RAM（重启丢失），但配置（紧急联系人等）通过 BLE 重设即可
- "安全模式什么时候退出？" → 连续运行 5 分钟 + 所有关键模块存活

### Q36. 30 分钟压力测试是怎么做的？结果怎么样？

**难度**：中级

**评委观察到的现象**：长时间演示系统稳定运行。

**参考答案要点**：
1. 测试设计：193 次操作按精确时序分派，4 阶段递增加压：
   - Phase 1 预热(0-5min, 30次)
   - Phase 2 中等(5-13min, 35次)
   - Phase 3 高负载(13-22min, 62次)
   - Phase 4 冲刺(22-30min, 66次)
2. 测 3 次的原因：验证行为确定性（三次关键指标标准差 <5%）
3. 结果：
   - 0 次 WDT 复位
   - 23/23 模块在线
   - 内存零泄漏（67KB 稳定）
   - 主循环 14.4ms（调度 69.6Hz）
   - 192/193 操作成功（99.5%）

**评委可能追问**：
- "1 次操作失败是什么？" → BLE 连接断连瞬间的 notify 发送失败，重连后恢复
- "内存怎么验证零泄漏？" → 三次测试内存趋势一致（116KB→67KB），结束点=最低点不再下降

### Q37. 系统崩溃后怎么自动恢复？

**难度**：中级

**评委观察到的现象**：长时间运行不崩溃；如果追问崩溃怎么办。

**参考答案要点**：
1. WDT 硬件看门狗：8s 超时，系统卡死后自动复位重启
2. 复位原因检测：启动时检查 reset_cause()，WDT_RESET 则打印告警（知道是崩溃重启而非正常开机）
3. 安全模式：连续 5 次 WDT 复位 → 放宽看门狗检测（任意模块存活即可喂狗）→ 避免无限重启循环
4. 两阶段初始化：重启后 LCD 先显示开机画面，后台初始化其他模块，3s 系统就绪
5. 模块初始化失败：跳过该模块的 tick，系统监控告警；CRITICAL 模块失联 → WDT 复位再尝试

**评委可能追问**：
- "如果总是同一个模块导致崩溃？" → 安全模式放宽检测让系统先运行，5 分钟稳定后恢复正常模式；如果 5 分钟内又崩溃，继续安全模式
- "重启后紧急联系人配置还在吗？" → 运行时数据在 RAM 重启丢失，但可通过 BLE 重新配置（小程序端保存配置）

### Q38. 内存够用吗？会不会耗尽？

**难度**：中级

**评委观察到的现象**：长时间运行不卡顿不崩溃。

**参考答案要点**：
1. STM32F413ZH：320KB SRAM，当前使用约 133KB，剩余 67KB（57% 空闲）
2. 内存管理：GC 阈值 8000 bytes（低于此值执行 gc.collect），压力测试 GC 约 1 次/秒
3. 内存零泄漏验证：30 分钟压力测试 ×3 次，内存稳定在 67KB 不再下降
4. 可扩展余量：67KB 可支撑 LCD 帧缓冲 16KB + 导航路线缓存 8KB 或 3-5 个新模块
5. 内存优化：DisplayService 开机图片数据释放后降低 26KB 使用

**评委可能追问**：
- "MicroPython GC 有什么特点？" → 16 字节定长块分配器，不做空闲块合并；反复分配/释放大块导致碎片化（线程栈 4KB 不回收）
- "线程栈 4KB 不回收怎么办？" → 改用持久线程（栈只分配一次，不再反复创建/销毁），避免碎片化

### Q39. 模块失联怎么检测？有什么陷阱？

**难度**：高级

**评委观察到的现象**：系统监控页显示所有模块在线（如果评委看到 LCD/小程序显示模块状态）。

**参考答案要点**：
1. 心跳机制：每个模块每轮 tick 更新心跳时间戳，系统监控每 5s 全量扫描
2. 三级分类处理：
   - CRITICAL（碰撞/报警/BLE）失联 → 停喂 WDT → 8s 复位重启
   - IMPORTANT（传感器/显示）失联 → 告警
   - AUXILIARY（其余）失联 → 仅记录日志
3. 关键陷阱：省电模式下采样间隔变长（温度 30s），心跳如果放在采样守卫之后则 30s 才更新一次，超过 15s 超时阈值 → 误判离线
4. 修复：心跳必须放在 tick 最前面（14 个模块修复），省电模式下心跳仍每 10ms 更新

**评委可能追问**：
- "为什么碰撞/报警/BLE 是 CRITICAL？" → 碰撞检测是安全核心，报警是救援核心，BLE 是唯一用户通道；三者失联系统失去安全价值
- "误判离线会导致什么？" → CRITICAL 误判 → 不该停喂 WDT 的停喂了 → 不该复位的复位了；已修复确保不误判

### Q41. 心率传感器初始化会导致其他模块超时，这个问题怎么排查解决的？

**难度**：挑战

**评委可能追问场景**：评委看到心率数据正常显示，可能追问开发中遇到什么问题。

**参考答案要点**：
1. 现象：心率传感器初始化后，音频/BLE/SMS/GNSS 的 AT 命令全部超时（15s+）
2. 排查方法（逐步排除法）：
   - 排除 GNSS 抢占 → 问题依旧
   - 排除初始化顺序 → Audio 移到心率前问题消失 → 确认心率导致
   - 排除 time.sleep → 删除后问题依旧
   - 定位到 UART9 初始化 → 测试所有 UART 编号 → 只有 UART9 导致问题
   - 修复：换 UART5（TX=PC12, RX=PD2），验证 UART5 不影响 AT 通道 ✅
3. 底层机制未明：不涉及引脚冲突，EC200U 用 USART6；但通过实测验证 UART5 安全
4. 教训：外设初始化可能影响通信模块，需要逐步排除法定位

### Q42. 主循环曾经从 15ms 膨胀到 100ms+，怎么排查修复的？

**难度**：挑战

**评委可能追问场景**：评委关注系统实时性，可能追问有没有遇到过性能问题。

**参考答案要点**：
1. 四个阻塞问题逐一修复：

   - 24 模块数据全量串口打印 → 87ms 阻塞 → 删除调试打印

**评委可能追问**：

### Q43. 反复创建线程会导致内存耗尽，这个问题怎么发现解决的？

**难度**：挑战

**评委可能追问场景**：评委关注内存管理。

**参考答案要点**：
1. 现象：NavigationService 测试中反复创建/销毁实例 → test_08 报 `Malloc failed`
2. 根因：MicroPython 线程栈从 C 堆分配 4KB（ALLOC_RAW 类型），gc.collect() 不回收 → 反复分配/释放导致碎片化 → 找不到连续 256 块区域
3. 解决：改用持久线程+队列模式——init 中启动 1 个持久线程，4KB 栈只分配 1 次，队列串行处理
4. 为什么持久线程能解决：4KB 只分配一次不再碎片化，队列串行无需互斥锁，线程生命周期与模块一致
5. 所有后台通信模块都采用持久线程：BLEService、AlarmService、NavigationService、GNSSDriver

**评委可能追问**：
- "为什么不做块合并？" → MicroPython GC 优先简单快速，块合并需要额外 CPU 和临时内存，嵌入式不适合
- "7 个子线程总栈消耗多少？" → 约 40KB（部分 8KB 栈），320KB SRAM 仍有 67KB 余量

### Q44. 事件总线 publish 后不处理会导致功能失效，这个陷阱怎么避免？

**难度**：高级

**评委可能追问场景**：评委关注架构设计细节。

**参考答案要点**：
1. 陷阱：EventBus.publish() 只入队不触发回调，必须调用 pump() 才处理事件
2. 表现：忘记 pump → 订阅者回调不执行 → 功能失效（测试中 90% 的集成测试 bug 根因）
3. 设计原因：避免回调重入（publish 在 tick 内调用，回调中再 publish 会导致递归）；主循环统一控制处理时机
4. 正确模式：主循环中 tick() → pump() → sleep，所有事件在 pump 阶段统一处理
5. 测试固定模式：操作 → tick() → pump() → 断言

**评委可能追问**：
- "为什么不在 publish 时直接触发回调？" → 避免 tick 内回调重入（回调中再 publish 导致递归），队列模式天然防重入
- "延迟一个 tick（10ms）会影响实时性吗？" → 碰撞检测在 IMU tick 中实时判决，报警在下一轮 pump 触发，总延迟 <15ms，骑行场景足够

### Q46. 控制状态回推有时序错误，这个问题怎么发现解决的？

**难度**：高级

**评委可能追问场景**：评委关注 BLE 控制闭环的正确性。

**参考答案要点**：
1. 问题：ControlService 通过订阅自己发布的事件来更新状态，但回推在事件处理之前就发送了快照 → 发送的是旧状态
2. 时序分析：执行指令 → publish 事件 → 立即回推（此时事件还未被 pump 处理，状态未更新）
3. 解决：直接在执行指令时更新状态，不通过事件回推；事件只用于通知其他模块
4. 设计原则：自己更新自己的状态不需要事件，事件只用于跨模块通知
5. 类似问题：报警取消后紧接着灯光开启，TTS 防抖会阻塞灯光 TTS → 报警取消时直接调用 TTS 绕过防抖

**评委可能追问**：
- "为什么不直接调用其他模块方法？" → 架构约束：模块间禁止直接调用，必须通过事件总线；但自己更新自己不需要事件
- "怎么区分合法自订阅和问题自订阅？" → 自订阅接收其他模块事件（如自动省电）是合法的；自订阅自己发布的事件来更新状态是问题

### Q47. BLE 推送消息有时会失败，这个问题怎么排查的？

**难度**：高级

**评委可能追问场景**：评委关注 BLE 通信可靠性。

**参考答案要点**：
1. 现象：ControlState 消息 notify 返回 `+CME ERROR: 53`（发送失败）
2. 根因：EventBus 自动注入 source/timestamp 字段，payload 从 16 字节膨胀到 66 字节，超 ATT_MTU
3. 排查：① 确认原始消息字节数 ② 确认 notify 发送的字节数 ③ 对比发现多了注入字段
4. 解决：BLE 转发时剥离 EventBus 自动注入字段，只保留业务字段
5. 经验：BLE payload 必须考虑注入字段影响，压缩格式需预留空间

**评委可能追问**：
- "MTU 协商后还有这个问题吗？" → 协商后载荷 244 字节，大部分消息不超；但协商前默认 20 字节载荷，仍需压缩
- "为什么 EventBus 要自动注入字段？" → 便于调试追踪事件来源；BLE 场景需要在转发时剥离

### Q50. 夜间骑行光线变暗，灯光怎么自动调节？

**评委观察到的现象**：小程序有骑行主页、控制页、登录页。

**参考答案要点**：
1. index 骑行主页：速度/位置/心率/血氧/温湿度/电量/轨迹地图
2. control 控制页：灯光开关/亮度调节/音量调节/省电模式/报警控制
3. login 登录页：用户认证
4. 自定义 TabBar：底部 3 个 Tab 切换页面

**评委可能追问**：
- "页面切换时 BLE 数据不丢吗？" → StateService 全局回调中心 → EventBus 广播 → 页面切换不丢数据
- "轨迹数据页面切换会丢失吗？" → trackPoints 在 RideService 模块级变量，页面从 Service 读取，不丢

### Q59. 小程序 BLE 数据怎么统一处理？

**难度**：中级

**评委观察到的现象**：所有页面数据一致，没有不同步。

**参考答案要点**：
1. StateService 全局回调中心：BLE onData → StateService 解析 → 按消息类型(t字段)分发 → EventBus 广播 → 各页面订阅更新
2. 为什么需要统一处理：原来 index.js 和 control.js 各有 onData 处理逻辑 → 状态不同步（P1 Bug）
3. 必须在 app.js onLaunch 中初始化：否则 _app/_bus 为 null，所有事件不触发
4. 消息类型路由：t=0 传感器数据、t=5 报警、t=7 控制状态、t=99 心跳

**评委可能追问**：
- "为什么不在每个页面各自监听 BLE？" → 页面切换监听可能丢失，多页面同时监听导致重复处理；统一入口保证一致性
- "非活跃页面能收到事件吗？" → 能，EventBus 广播到所有订阅者；切换回来时从 Service 读取最新状态

---

### Q60. 小程序骑行轨迹怎么保证不丢失？

**难度**：中级

**评委观察到的现象**：页面切换后轨迹仍在地图上显示。

**参考答案要点**：
1. trackPoints 数据所有权：从 Page data 迁移到 RideService 模块级变量
2. 原问题：trackPoints 在 Page data 中，页面切换（index→control→index）可能清空
3. 数据流：BLE 接收 t=0 → StateService → RideService 追加 trackPoints → 页面从 RideService.getTrackPoints() 读取
4. 结束骑行时必须在 RideService.clear() 之前获取轨迹数据

**评委可能追问**：
- "为什么不存本地存储？" → 骑行中频繁写入影响性能；RideService 内存存储足够
- "最多存多少轨迹点？" → 小程序内存比设备充裕，但仍需控制（最多约 5000 点）

---

### Q61. BLE 重连时"适配器已打开"错误怎么处理？

**难度**：中级

**评委可能追问场景**：评委关注 BLE 连接稳定性。

**参考答案要点**：
1. 问题：BLE 连后重连时 wx.openBluetoothAdapter 报 "already open"
2. 处理：捕获错误 → setCallbacks 更新回调 → 直接扫描（不重新 open）
3. 不 close 再 open：close 会断开已有连接，重连场景应复用适配器
4. BLE 数据回调监听所有特征值变化，必须按 characteristicId 过滤

**评委可能追问**：
- "BLE 断连后自动重连吗？" → 当前需用户触发或页面切换时重连；可实现自动重连但需注意间隔
- "多设备 BLE 连接？" → 当前只支持 1 个 Central 连接

## 附录 B：核心架构决策速查表

> 评委问"为什么不选X方案？"时的快速回答

| 评委可能问 | 我们的回答 |
|:----------|:----------|
| "为什么不用 RTOS？" | MicroPython 事件驱动已满足实时性，开发效率比 RTOS 高 3-5 倍，调度 69.6Hz CPU 70% 空闲 |
| "为什么不用 MQTT 云端？" | BLE 直连低延迟(<100ms)、无云端依赖、架构简单(Device↔BLE↔小程序)，骑行户外必须有 |
| "为什么不用 ESP32？" | ESP32 WiFi 不适合户外，BLE 不如 EC200U 稳定，无蜂窝通信；EC200U 五合一降低硬件复杂度 |
| "为什么不用 C 语言？" | 竞赛时间紧迫，MicroPython 开发效率高 3-5 倍，实测性能足够(154μs/tick) |
| "为什么心率用 UART5？" | UART9 初始化破坏 AT 通道导致音频/BLE/SMS/GNSS 全超时，UART5 经验证安全 |
| "为什么用持久线程？" | MicroPython GC 不回收线程栈(4KB)，反复创建/销毁导致碎片化 Malloc failed |
| "为什么 WDT 不无条件喂狗？" | CRITICAL 模块卡死时停喂让系统复位，恢复安全功能；无条件喂狗会让系统"假活" |
| "为什么合并 3 条 BLE 为 1 条？" | 密集指令 3 条/次×5 次/s=15 条 notify 队列爆炸；合并为 1 条/tick 恒定不爆炸 |
| "为什么碰撞三级判决？" | 单点判断无法区分脉冲宽度和振荡特征，滑动窗口+鉴别器提供时间维度信息防误报 |
| "为什么 BLE 不用 INDICATE？" | NOTIFY 不需要客户端确认延迟更低(<100ms)，适合实时数据推送 |

## 附录 C：高频追问 Top 10

> 最可能被评委深入追问的问题及一句话回答

1. **碰撞误报怎么防？** → 三级判决（归一化+四级阈值+三鉴别器），6 种实测场景验证，桌面平移/抖动/拿取不误报
2. **低电量安全功能中断吗？** → EMERGENCY 模式保留碰撞/报警/BLE 三个 CRITICAL，IMU 仍每 100ms 采样
3. **BLE 断连后报警怎么办？** → 本地声光+SMS 不依赖 BLE，核心安全功能本地独立运行
4. **手机密集发指令会崩溃吗？** → 快照合并 3 条→1 条，最多 1 条/tick 推送，30 分钟压力测试 99.5% 通过
5. **系统崩溃怎么恢复？** → WDT 8s 硬件看门狗自动复位重启，CRITICAL 模块失联→停喂→复位→恢复安全功能
6. **为什么选 MicroPython 不选 C？** → 开发效率高 3-5 倍，实测性能足够(154μs/tick, 69.6Hz, CPU 70% 空闲)
7. **心率 UART 为什么换口？** → UART9 初始化破坏 AT 通道导致其他模块全超时，UART5 经验证安全
8. **碰撞检测响应速度？** → IMU tick 实时判决 <1ms + pump 回调 <10ms = 总延迟 <15ms
9. **长时间运行稳定吗？** → 30 分钟×3 次压力测试，0 次 WDT 复位，23/23 模块在线，内存零泄漏
10. **导航和报警冲突？** → 报警优先级 > 导航，报警期间导航 TTS 暂停，报警取消后恢复
